# M1a-0 spike: better-auth on Workers and D1

A time-boxed, throwaway prototype that answers the feasibility list in TDD §10 ("New in v1.7") and PLAN §4 M1a-0 before M1a builds on better-auth. **Nothing here is imported by the app.**

It runs a Hono Worker on workerd (through `@cloudflare/vitest-plugin` and `wrangler dev`) with a D1 binding, on the repository's compatibility date (`2026-11-01`). better-auth is configured the way TDD §8.1 describes: our table names, magic links behind our confirmation POST, passkeys with an enrolment ticket, `__Host-` cookies, the default-deny allowlist and a token-stripping filter.

## Recommendation: **GO**, with the workarounds below

All three no-go criteria in PLAN §4 / TDD §10 pass:

| No-go criterion | Result | Evidence |
|---|---|---|
| Fails on D1 without transactions | **Passes.** better-auth detects D1, turns transactions off and runs multi-step writes as ordered statements. Partial writes can happen, and our ordered steps and repair job cover them. Single-row consumes (verification values, magic-link tokens) are one atomic `DELETE … RETURNING`. | `test/d1-adapter.test.ts`, `test/magic-link.test.ts` (concurrency) |
| `user.create.before` can't be shown to cover every creation path | **Passes.** Every user insert in the loaded code goes through `createWithHooks(…, "user")`. A static scan finds no raw insert. Each reachable path is refused without our server-set marker. | `scripts/creation-paths.mjs`, `test/hooks.test.ts` |
| No hook (or library error) reliably exposes counter regressions | **Passes, with one workaround.** SimpleWebAuthn already enforces our exact rule. better-auth hides it behind a generic `AUTHENTICATION_FAILED`, but an `after` hook can re-verify the refused assertion and tell a real clone from any other failure. The library's own log line also names it. Proven end to end with a cloned virtual authenticator. | `scripts/passkey-e2e.mjs` (step D) |

Nothing failed outright. Several defaults are unsafe or don't match our design, though: user verification isn't enforced, the passkey origin comes from the request's `Origin` header, the session token appears in JSON bodies, the cookie prefix is wrong, and secret rotation signs everyone out. Each has a small, tested workaround (listed below). M1a must carry all of them.

## How to run

```sh
cd spikes/better-auth
npm install --legacy-peer-deps
npm test                 # 81 Workers-runtime tests (vitest-plugin, D1, nodejs_compat)
npm run test:e2e         # wrangler dev + Playwright Chromium virtual authenticator (needs /opt/pw-browsers)
npm run typecheck
npm run schema           # SQL from better-auth's getMigrations (defaults and our mapping) + diff against migrations/0001
npm run creation-paths   # static scan: every user-creating call site
npm run nodejs-compat    # nodejs_compat across compatibility dates (wrangler dev)
npm run bundle-size      # esbuild sizes + per-package breakdown
npm run cost             # CPU cost of a new instance and a session read (Node)
npm run advisories       # published advisories against the pinned versions
```

Stability: `npm test` passed three consecutive runs, and the end-to-end script passed three runs.

## Workarounds M1a must carry

1. **Epoch-ms dates:** pass our own Kysely (`database: { db, type: "sqlite" }`) with `EpochMsPlugin`, or accept ISO TEXT for better-auth's own date columns and record the exception in platform §14.
2. **User verification:** `registration.afterVerification` and `authentication.afterVerification` refuse `userVerified === false`. Registration options use `authenticatorSelection: { residentKey: "required", userVerification: "required" }`. An `after` hook rewrites the authentication options to `userVerification: "required"`.
3. **Passkey `origin` set explicitly** to the canonical origin (otherwise the request's `Origin` header is trusted), and `rpID` from the installation record.
4. **Clone detection:** a `before` hook captures the challenge; the `after` hook re-verifies a refused assertion and raises `clone_detected` and the `security_notice`. Drop `verified_sign_count`.
5. **`createSession` on registration verify:** force it on for enrolment-ticket registrations and strip it when a session exists.
6. **Enrolment ticket:** read in `resolveUser` (options) and consumed by compare-and-set in `registration.afterVerification` (verify), before any write.
7. **Token filter** on the better-auth mount (drop `token` keys and token-valued strings), and never pass `magicLinkVerify`'s body through.
8. **`__Host-` cookies:** `useSecureCookies: false`, `cookiePrefix: "__Host-officebox"`, and `defaultCookieAttributes` with `secure: true`.
9. **CSRF header required on the two GET options routes** as well as on every state change.
10. **Server-set marker** through AsyncLocalStorage; server code creates users through `internalAdapter.createUser`.
11. **Step-up:** veto the session in `session.create.before` while in a `reauth` context, then update the current session's `fresh_auth_at`.
12. **Forward `getSession` Set-Cookie headers** from every route and middleware that reads the session.
13. **Users are created with `emailVerified: true`** (the invitation or setup email is the proof). A magic-link verify for an unverified user runs `revokeUnprovenAccountAccess`, which deletes that user's accounts and sessions.
14. **Explicit options:** `rateLimit.enabled: true` with the D1 `consume` storage, `telemetry.enabled: false`, `advanced.database.joins: true`, `nodejs_compat` in `wrangler.jsonc`, and optionally `validateSchema: false` in production.
15. **Secret rotation** signs everyone out (document it), or re-sign old cookies in our middleware.
16. **Upgrade checks in CI:** `creation-paths`, the UV and clone end-to-end tests, the token sweep, and `advisories`.

## Spec and TDD statements that turn out wrong or imprecise

- **TDD §10 (M0 foundation) and §8.1:** "`@simplewebauthn/server` 14.0.3 … comes through better-auth's passkey plugin". `@better-auth/passkey` 1.7.15 depends on **SimpleWebAuthn 13.x** (13.3.3).
- **TDD §8.1 configuration table, passkey row:** "user verification required … and required when verifying". This **can't be configured**: the plugin passes `requireUserVerification: false` and hardcodes `"preferred"` in the authentication options. It is enforced through our hooks (workaround 2). The table should also add the plugin's `origin` option (workaround 3).
- **TDD §8.1 "Passkey counter rule", option 2** (a before hook reads `verified_sign_count`, the after hook compares): as written it **can't see regressions**, because the library rejects them before any passkey hook runs. Replace it with the decision in 3c.
- **TDD §8.1 and Identity §6:** passkey "authentication options · `POST /auth/sign-in/passkey`". In 1.7.15 the routes are **`GET /passkey/generate-authenticate-options`** and **`POST /passkey/verify-authentication`**; the registration routes are `GET /passkey/generate-register-options` and `POST /passkey/verify-registration`. The options routes are GETs with side effects (TDD §3.1/§8.2: "state-changing requests need the header" should list them).
- **TDD §8.1 / Platform §16:** "rotation through `BETTER_AUTH_SECRETS`". The format is `<version>:<secret>,…`, newest first, and **rotation invalidates every session cookie**.
- **Identity §4.4 / TDD §8.1, magic-link request:** "the lookup and a token write run either way". better-auth itself does **no lookup** on request; both happen only in our `sendMagicLink`, which is where equal work must be enforced.
- **TDD §8.1 "Runtime"** (`nodejs_compat` on by default from 2026-08-04, to verify): **confirmed locally** (2026-08-03 off, 2026-08-04 on). The root `wrangler.jsonc` has no `compatibility_flags`; add `nodejs_compat` explicitly anyway.
- **Identity §5 `passkeys`:** `created_via TEXT NOT NULL` with no default can't be inserted by better-auth (it doesn't know the column). It needs a DB default, set afterwards by our after hook (as in the spike). better-auth also requires `device_type` and `backed_up` NOT NULL, and its `created_at` is nullable.
- **Identity §5 / platform §14:** "Timestamps are epoch milliseconds where the adapter allows". The adapter **doesn't** by default (ISO TEXT); epoch ms needs the Kysely plugin (1c).
- **TDD §8.1 / Identity §4.5, sessions:** "Every authenticated request loads the session through better-auth". The read can **refresh the session and emit Set-Cookie** (once a day), which callers must forward (12b).
- **Identity §4.5 "session-delete hook":** it exists (`session.delete.after`, per row on every revoke path), but expiry fires nothing until the cookie is next presented. The UserHub recheck stays.

## What this spike did not verify

- **Production Cloudflare.** Everything ran on local workerd: vitest-plugin/Miniflare and `wrangler dev`. Not checked: production D1 behaviour (`changes()` in batches, read-replica lag, primary reads), the `nodejs_compat` default on deployed Workers, and the deployed upload size (`--dry-run` only).
- **GitHub advisory pages** for GHSA-fvxx-76fc-893x and the passkey origin/UV advisory TDD §8.1 cites: the GitHub API was blocked (403) and adding the better-auth repository to the session was denied. The advisory check used npm's bulk endpoint (GitHub Advisory Database data) instead.
- **`npx auth generate`** itself: the SQL came from `getMigrations` run programmatically, which is the code the CLI uses for Kysely. The CLI package (`auth`) was not installed.
- **Isolate start-up time** for the 1.19 MB bundle (cold-start parse). CPU numbers are Node V8 measurements of library work, not workerd wall time.
- **Real email delivery and production timing** for the magic-link enumeration check: only local medians were measured, with a 1 to 2 ms gap from our own callback.
- **Concurrent passkey sign-ins racing the library's plain counter UPDATE** (it isn't compare-and-set). The library refuses replays through the single-use challenge, and real regressions through SimpleWebAuthn; a lost update can only lower the stored counter.
- **Domain move end to end:** only checked that a second instance for another origin can coexist and refuses the first origin's Origin; registering on a second origin wasn't run.
- **Spec-level behaviour outside the feasibility list** (invitations, the repair job, `GET /me` contents, security-notice banner) is out of scope; the spike only proves the library seams those features need.
